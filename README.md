# Associates AI Search Platform

A small, runnable reference implementation of **enterprise knowledge search with Elasticsearch,
extended with AI and agentic capabilities**. It models an internal "knowledge portfolio" at a
consulting firm, where associates search historical case summaries, industry reports, proposals and
methodology guides, and where associates staffed on a client can ask questions about *their* client
("Where is Wrenfield North Hospital located?", "Is cardiology supported there?").

All documents, clients, companies and people in this repo are **fictional** and generated by
[`data/generate_corpus.py`](data/generate_corpus.py).

## What it demonstrates

| Area | Where | What to look at |
|---|---|---|
| Index design | [`index_schema.py`](backend/app/index_schema.py) | Separate index/search analyzers, search-time `synonym_graph`, keyword facets, strict mapping, `int8_hnsw` dense vectors |
| Ingestion | [`ingest.py`](backend/app/ingest.py), [`chunking.py`](backend/app/chunking.py) | Structure-aware chunking with contextual headers, bulk loading with refresh off, blue/green reindex behind an alias |
| Retrieval | [`search.py`](backend/app/search.py) | BM25 with field boosts and phrase bonus, kNN with pre-filters and a similarity floor, hybrid via reciprocal rank fusion, document-level facets |
| Re-ranking | [`rerank.py`](backend/app/rerank.py) | Cross-encoder second stage over the top 30 results, blended with the first-stage order when the query names a client or hospital |
| Security | [`security.py`](backend/app/security.py) | Document-level ACL filter on every query, including kNN and every agent tool call |
| RAG answers | [`rag.py`](backend/app/rag.py) | Numbered sources, grounded answers with citations, offline extractive fallback |
| Agentic search | [`agent.py`](backend/app/agent.py) | Claude tool-use loop over search tools (search, case examples, experts, read document, filter values), with a bounded number of steps and a full trace; offline rule-based planner |
| Query understanding | [`query_understanding.py`](backend/app/query_understanding.py) | Pulls industry, document type, dates and intent out of queries; recognises client and hospital names (including short forms and typos such as "Queenmoor") as boosts |
| Client-specific Q&A | [`healthcare_clients.py`](data/healthcare_clients.py), [`search.py`](backend/app/search.py), [`rag.py`](backend/app/rag.py) | Client and facility fact sheets, a "my clients" retriever for staffed associates, follow-up questions that carry over the hospital or client being discussed |
| Evaluation | [`eval/`](eval/) | Judged queries; nDCG@10, MRR@10, Recall@10 and latency for each retrieval mode |

## Quick start

Requirements: Docker Desktop (about 3 GB RAM free) and `make`.

```bash
cp .env.example .env
```

```bash
make up      # Elasticsearch 8.15 + FastAPI on http://localhost:8000
```

```bash
make seed    # chunk, embed and index the 134 fictional documents (first run downloads a ~130 MB embedding model)
```

Open http://localhost:8000. Try these:
- **Search**, with *Auto-filters* on: `branch and digital banking case studies`
- **Client questions:** set *Viewing as* to "Associate on Wrenfield Health team", open **Ask**, and have a
  conversation:
  1. `Where is Wrenfield North Hospital located?`
  2. `Is cardiology supported there?` (the follow-up is understood as being about Wrenfield North Hospital)
  3. `Which Wrenfield hospitals do open-heart surgery?`
- Switch *Viewing as* back to "Associate (not on a client team)" and ask the same question: nothing comes
  back. Every user is an internal associate, but client-restricted documents are visible only to
  associates staffed on that client's team.
- **Ask**: `How have we helped banks move customers to digital channels?`
- **Agent**: `Who are our experts on retail banking, and what did their projects achieve?`

Other targets:

```bash
make eval    # relevance and latency report -> eval/results.md
```

```bash
make test    # unit tests (no Elasticsearch or LLM needed)
```

```bash
make kibana  # optional Kibana on http://localhost:5601
```

### Turning on the LLM (Claude)

Without an LLM the demo runs fully offline. The Ask tab gives extractive answers with citations and
the Agent tab uses a rule-based planner over the same tools. To use Claude, edit `.env`:

```
LLM_PROVIDER=anthropic          # or: bedrock (uses the AWS credential chain + AWS_REGION)
ANTHROPIC_API_KEY=...
LLM_MODEL=claude-opus-5-5
```

Then run `docker compose up -d api`.

## Results on the sample corpus

From `make eval` (21 judged queries including 5 client-specific ones, 134 documents, local `bge-small`
embeddings, single-node Elasticsearch on a laptop; latency varies with machine load):

| mode | nDCG@10 | MRR@10 | Recall@10 | p50 ms |
|---|---|---|---|---|
| BM25 | 0.788 | 0.921 | 0.769 | 12 |
| Vector (kNN) | 0.865 | 0.897 | 0.868 | 23 |
| Hybrid (RRF) | 0.910 | 0.952 | 0.915 | 41 |
| Hybrid + query understanding | 0.881 | 0.976 | 0.927 | 31 |
| Hybrid + cross-encoder re-rank (entity-aware) | **0.915** | 0.929 | 0.887 | ~500 to 1,000 |
| Hybrid + query understanding + re-rank | 0.899 | **1.000** | **0.935** | ~500 to 1,000 |

What the numbers say:
- **Hybrid beats either retriever on its own.** BM25 misses vocabulary mismatches such as "lender" vs
  "bank" or "grocer" and "click and collect" vs "retail" and "omnichannel". Vectors miss exact terms and acronyms. RRF combines
  them without having to tune score scales.
- **Client and facility questions are answered precisely** (nDCG 1.0 for "Where is Wrenfield North
  Hospital located?") because names are recognised and boosted, and fact sheets carry the facts.
- **Query understanding is a trade-off.** It lifts MRR (the first result is right more often: 0.952 →
  0.976, and 1.000 with re-ranking) but lowers nDCG, because hard filters over-read some queries. For
  example, "report" filters "insurance pricing benchmark report" down to reports only. That is why client
  and hospital names are applied as *boosts*, not hard filters, and why low-confidence extractions
  should be boosts too.
- **Re-ranking needs care.** A cross-encoder sees only the question and the passage, not the signals the
  first stage used (entity boosts, the "my clients" retriever). Used on its own, it *hurt* "Is cardiology
  offered at Wrenfield Lakeside?" (nDCG 1.00 → 0.63) by promoting the hospital with the most cardiology
  content. Three strategies were compared on the same judged set (`RERANK_STRATEGY`, hybrid + re-rank):

  | strategy | nDCG@10 | Lakeside question |
  |---|---|---|
  | `replace`: cross-encoder order only | 0.897 | 0.63 |
  | `blend`: always fuse the first-stage and cross-encoder ranks | 0.921 | 1.00 |
  | `entity_aware` (default): blend only when a client or hospital is named | 0.915 | 1.00 |

  `replace` was the worst on every corpus version tried. `blend` and `entity_aware` swapped places
  between versions, and a 0.006 gap on 21 queries is noise, so either is defensible. The real lesson is
  never to trust a re-ranker blindly. It also costs hundreds of milliseconds on CPU, so use it on the top
  results only.
- **Natural-language questions need different handling from keyword queries.** In keyword-only mode,
  natural questions such as "How have we helped banks move customers to digital channels?" returned nothing: "how", "have"
  and "we" counted towards BM25's minimum-should-match. The search analyzer now drops question words,
  and the Ask flow retrieves with the understood keywords while the answer step sees the full question.
  The judged queries are keyword-style, so this didn't move the metrics; add question-style queries to
  the judged set to catch regressions like this.
- The corpus and judgments are small and synthetic. The *method* is the point: build a judged set, measure
  every change, and avoid tuning relevance on anecdotes.

## Notes

- Security is disabled on the local Elasticsearch container for convenience only. Any shared
  environment needs TLS, API keys and role-based access.
- On 8.15 with the free basic license, the native `rrf` retriever returns 403 (it needs a paid tier there). The app tries it in
  `hybrid_native` mode and falls back to the client-side RRF it uses by default.
- The *Viewing as* personas (`X-Demo-User` header) stand in for SSO. All of them are associates; they
  differ only in which client team they are staffed on (plus a knowledge team that curates all content).
  See `config.py` and `security.py`.
